## Overview

This is the agency-facing hub for a single student: one page (`student-detail-page.tsx`) with tabs for Review, Info, Documents, Applications, Notes, and History. It exists to answer three questions an agency staffer keeps asking: *is this profile ready to submit?*, *which universities is this student applying to?*, and *what's happened so far?* Rather than three separate pages hitting the API independently, one hook (`useStudentProfileData`) owns all the server state (profile, documents, application batches) and every tab reads from it. Readiness and history aren't stored anywhere — they're recomputed from that raw state on every render.

## Key Components

- `StudentDetailPage`: tab shell; owns only UI state (`activeTab`), delegates all data to the hook.
- `useStudentProfileData`: fetches profile+documents+batches in parallel on mount, polls the active batch every 5s, derives `resolvedTargets`/`pendingTargets`/`documentsByType`.
- `computeProfileReadiness`: pure function scoring 4 categories (personal/education/documents/language) into a completion percentage.
- `buildApplicationTimeline`: flattens `batches → applications → steps` into a single sorted event list for the History tab.
- `ApplicationTargetsPanel`: agency pastes a university's application form URL; backend resolves it to a university record instead of the agency searching a catalog.

## Concepts & Decisions

### Derived state instead of stored state

- **What**: `readiness` and the timeline `events` aren't fields on the student record — they're computed in the component/hook from `student` + `documents` + `batches` every render (`computeProfileReadiness(student, documents)` at [student-detail-page.tsx:77](apps/dashboard/features/students/components/student-detail-page.tsx#L77)).
- **Why used here**: A stored "readiness %" would drift the moment a document is deleted or a field is edited elsewhere — someone would need to remember to recompute and persist it. Deriving it keeps one source of truth (the raw records) and makes readiness *always* correct, at the cost of recomputing on every render (cheap here — plain array scans over small lists).

### Polling for async batch status

- **What**: While the latest application batch is "active" (submitting), the hook polls `getApplicationBatches` every 5s ([use-student-profile-data.ts:87-97](apps/dashboard/features/students/hooks/use-student-profile-data.ts#L87-L97)) instead of pushing updates.
- **Why used here**: Application submission is a backend job (likely browser automation against university forms — see `extension-bridge.ts` in the applications feature), and polling is the simplest way to reflect job progress without websocket/SSE infrastructure. Trade-off: up to 5s of staleness and wasted requests once the batch finishes, versus a push-based channel that reacts instantly.

### URL-driven university resolution

- **What**: Instead of the agency searching a university directory, they paste the application form's URL directly; `resolveUniversityByFormUrl` on the backend matches it to a known university record ([application-targets-panel.tsx:80](apps/dashboard/features/applications/components/application-targets-panel.tsx#L80)).
- **Why used here**: Matches how agencies actually work — they already have the form link from the university, not a name to search. It also lets the target list gracefully hold "unresolved" targets (`universityRaw` with no `universityId`) when the URL doesn't match anything yet, rather than blocking the agency from recording intent.
