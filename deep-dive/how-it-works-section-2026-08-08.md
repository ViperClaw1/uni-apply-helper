## Overview

This adds an autoplaying, looping mockup slideshow to the marketing landing page: a fake app window that cycles through filling a form, uploading documents, picking universities, submitting, and tracking status. The entire animation — including a progress bar and a "Submitting… → Submitted" transition inside individual slides — runs on pure CSS keyframes with zero JavaScript state, timers, or `useEffect`. The React components only render markup and static `style` objects; the browser's CSS animation engine drives everything else.

## Concepts & Decisions

### One shared timeline via negative `animation-delay`

- **What**: Every slide/sub-element uses the *same* `animation-duration` (`TOTAL_SECONDS = 4s × slideCount`) and the *same* `@keyframes` rule, whose percentages are written against that full duration. Each element gets `animation-delay: -${offset}s` — a negative delay immediately fast-forwards the animation to that point in its own cycle.
- **Why used here**: It's a way to fake "step N of a slideshow is active" purely in CSS. Instead of a JS `setInterval` incrementing an index and re-rendering, every slide plays the identical loop simultaneously, just phase-shifted — so the component tree never re-renders after mount and the file needs no `"use client"` state. The cost: the keyframe percentages (`2%, 9%`, `10.5%`, etc. in [globals.css](apps/dashboard/app/globals.css)) are hand-tuned magic numbers derived from `SLIDE_SECONDS`/slide count — changing the slide count or duration means recalculating every percentage by hand, since nothing generates them.

### Nested timelines within one slide's window

- **What**: `ApplySlide`'s "Submitting…" → "✓ submitted" swap and `StatusSlide`'s draft → in-progress → submitted badge cycle each use their own `@keyframes` (`how-it-works-apply-loading/done`, `how-it-works-status-a/b/c`), but bound to the *same* `TOTAL_SECONDS` duration and delay as the parent slide.
- **Why used here**: Lets a single slide show a mini state transition without introducing any JS timing at all — it's the same negative-delay trick applied recursively, carving that slide's ~10% window into narrower sub-bands (e.g. status-a owns 2%–4.3%, status-b owns 5.3%–6.6%, etc.).

### Discriminated union for slide data

- **What**: `HowItWorksSlide` in [how-it-works.ts](apps/dashboard/features/marketing/constants/how-it-works.ts) is a tagged union; TypeScript narrows `fields` to only exist on `kind: "form"`.
- **Why used here**: Keeps all slide *content* (including bilingual Russian/English form labels) in one data file, separate from the *rendering* logic in the component — adding a new form slide is a data edit, not a new component.
